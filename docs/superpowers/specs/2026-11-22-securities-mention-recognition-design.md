# 证券提及识别设计（用户提示词 → 指数/股票候选集）

## 1. 背景与目标

### 1.1 背景

Agent 场景下，用户提示词（自然语言）中可能以**代码或名称**提到若干指数（股票指数/债券指数）或股票。系统内有证券数据库（万级以内，含证券代码、全名、类型字段；简称/别名不全）。需要把用户提示词中的所有证券提及识别出来，映射为库内标准代码，供下游使用。

### 1.2 已确认的约束

| 维度 | 结论 |
|---|---|
| 数据库规模 | 万级以内（< 1 万条），字段：代码 + 全名 + 类型（股票/指数/债券指数） |
| 歧义策略 | **召回优先**：模糊/歧义命中返回全部候选（带分数），由下游 Agent 或用户再确认 |
| 链路与延迟 | 应答主链路上**同步执行**，可接受约 1–2s 额外延迟；允许调用大模型 chat |
| 可用能力 | LLM chat 调用可用；数据库为常规关系库（万级全量内存加载即可） |

### 1.3 一期目标

1. 对任意中文/混合用户提示词，输出其中所有证券提及的**结构化识别结果**：确定命中（recognized）、模糊候选（candidates）、库中无匹配（unmatched）三档。
2. 简称/口语叫法（如"茅台"）在 LLM 规范化辅助下可确定命中；库内别名不全不阻塞识别。
3. LLM 故障时自动降级为纯本地匹配，主流程不中断。

### 1.4 非目标（一期不做）

- 不做别名表的自动沉淀与回写（仅预留 unmatched 输出供人工积累）。
- 不做词典快通道省 LLM 调用（同步 1–2s 可接受，暂无必要）。
- 不引入 ES / 向量库 / 分词服务；万级数据用内存匹配。
- 不做证券实体链接之外的动作（如行情查询、历史消歧记忆）。

## 2. 方案选型（已评审）

| 方案 | 思路 | 结论 |
|---|---|---|
| **A. LLM 提取 + 确定性匹配层**（采纳） | LLM 负责从自然语言中提取提及并给出规范名建议；匹配层只认库内真实数据，负责校验、打分、分级 | ✅ 核心矛盾（叫法随意 vs 别名不全）由 LLM 解决；LLM 不可靠性由确定性匹配层兜住；匹配层纯函数可测试 |
| B. 纯词典/规则扫描 | Aho-Corasick + 代码正则，毫秒级零成本 | ❌ 别名不全导致简称漏召回，需长期维护别名表 |
| C. 词典打底 + LLM 兜底 | 先词典后 LLM，合并去重 | ❌ 两条链路合并复杂，同步场景下节省有限（YAGNI）；将来可从 A 平滑演进到 C |

## 3. 总体架构

```
用户提示词 ──► RecognitionPipeline（识别管线，同步 <2s）
                 │
                 ├─① CodeRegexScan      毫秒级：正则扫 6 位代码/带后缀代码，不依赖 LLM
                 │
                 ├─② MentionExtractor   一次 LLM chat（结构化输出，温度 0）
                 │      输出: [{text:原文片段, normalized:规范名建议, type:股票|指数|债券指数|未知}]
                 │      ⚠️ LLM 不输出代码，只输出提及和规范名建议（防幻觉）
                 │
                 ├─③ SecurityMatcher    内存匹配服务（启动时全量加载建索引）
                 │      对每个提及按级别匹配：L1–L5（见第 4 章）
                 │
                 └─④ Aggregator         合并去重、分级、输出
```

### 3.1 组件边界

| 组件 | 职责 | 依赖 |
|---|---|---|
| `CodeRegexScan` | 代码格式候选预扫（LLM 挂掉时的保底来源之一） | 无 |
| `MentionExtractor` | 自然语言 → 提及列表（原文片段 + 规范名建议 + 类型猜测） | LLM chat |
| `SecurityMatcher` | 提及 → 库内证券（分级匹配 + 打分） | 内存证券索引 |
| `Aggregator` | 合并正则与 LLM 来源、按 code 聚合去重、分档输出 | 无 |

`MentionExtractor` 不查库；`SecurityMatcher` 不碰 LLM。两者经 `ResolvePipeline` 编排，各自可独立单测。

## 4. 匹配级别定义（SecurityMatcher）

按级别从高到低尝试，**L1–L4 命中即确定；仅 L5 命中为候选**。

| 级别 | 名称 | 逻辑 | 示例 |
|---|---|---|---|
| L1 | 代码精确 | 提及符合代码格式（6 位数字、`000300.SH` 等），查码表 | `600519`、`000300.SH` |
| L2 | 全名精确 | 原文片段全等命中全名表 | `贵州茅台`、`沪深300指数` |
| L3 | 归一化精确 | 归一化函数（去空白、全角转半角、大小写折叠、去"指数"/"股份有限公司"等后缀、去标点）后全等比对；含双向包含判等 | `贵州茅台酒股份有限公司` → `贵州茅台` |
| L4 | 规范名命中 | LLM 的 `normalized` 建议走 L2/L3 | `茅台` → 规范名 `贵州茅台` → 命中 |
| L5 | 模糊兜底 | rapidfuzz 对全量打分取 top-N（双向部分比率 + 编辑距离 + 拼音首字母缩写如 GZMT），返回带分数候选 | `平安` → 平安银行 0.86 / 中国平安 0.71 |

- 万级全量线性打分（rapidfuzz C 实现）毫秒级，无需预建模糊索引。
- 分数仅用于**候选排序**，不参与分档；分档只看匹配级别。

## 5. 输出契约

```json
{
  "recognized": [
    {"mention": "茅台", "code": "600519.SH", "name": "贵州茅台",
     "type": "stock", "level": "L4", "source_text": "茅台最近走势"}
  ],
  "candidates": [
    {"mention": "平安", "items": [
      {"code": "000001.SZ", "name": "平安银行", "score": 0.86},
      {"code": "601318.SH", "name": "中国平安", "score": 0.71}
    ]}
  ],
  "unmatched": ["某概念股"],
  "degraded": false
}
```

- `recognized`：L1–L4 确定（含正则来源校验通过的代码）。
- `candidates`：仅 L5 命中，按 score 降序，默认 top 3。
- `unmatched`：LLM 提取到但库中无任何 L1–L5 命中。
- `degraded`：LLM 失败降级时为 `true`。
- 同一 code 多处提及在 `Aggregator` 按 code 聚合，保留首个 mention 原文。

## 6. 错误处理

| 故障 | 处理 |
|---|---|
| LLM 超时（>3s）/调用失败 | 降级为纯本地匹配（L1–L3 + L5，仅丢 L4），`degraded: true`，流程不中断 |
| LLM 输出非法 JSON | 带错误信息重试 1 次，再失败同上降级 |
| LLM 幻觉（编造提及/代码） | 结构上免疫：LLM 只产提及文本；最终一切以匹配层查库结果为准，LLM 给的代码最多当 hint 复核 |
| 数字误报（"涨了 500 点" → 000500） | 正则命中要求上下文验证：代码需独立成词（前后不是数字/量词）才进结果；提取 prompt 明确排除叙述性数字 |
| 同义重复（"茅台""贵州茅台"同现） | Aggregator 按 code 聚合去重 |

## 7. 测试策略

1. **匹配层单测**（纯函数，主力）：代码精确 / 全名 / 归一化 / 拼音缩写 / 歧义 top-N / 数字误报排除 / 空输入；断言级别与分数区间。
2. **提取层评测集**：20–50 条真实风格 prompt 的 golden set（含"茅台""中证500""国债指数""没有证券"等），定期跑 LLM 对比提及召回率/误报率；只出报告，不卡 CI（LLM 有波动）。
3. **端到端冒烟**：完整句子 → 断言输出 JSON 结构与关键命中。

## 8. 演进路径（一期不做，仅预留）

- **别名沉淀**：`unmatched` 中人工确认过的叫法积累为别名表 → L5 命中率上升；别名足够多时可加"词典快通道"跳过 LLM（演进为方案 C 形态）。
- **规模扩展**：库涨到十万级以上时，匹配层换批量打分（`rapidfuzz.process.cdist`）或 n-gram 倒排，对外 API 不变。

## 9. 决策记录

- 2026-11-22：方案探索评审通过，采纳方案 A（LLM 提取 + 确定性匹配层）；分档规则定为"级别定档、分数仅排序"；数据库确认含类型字段。
